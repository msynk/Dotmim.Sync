Setup & Options
=================

Two objects describe how a sync session runs:

* ``SyncSetup`` describes **the schema** to synchronize. Tables, filters, prefixes and suffixes used to name the sync metadata. The setup is **shared** between the server and all the clients of a given scope.
* ``SyncOptions`` carries **per-process** settings. Batch directory, batch size, transaction mode, error policy, etc. The same options can have different values on the server and on each client.

In **HTTP mode** the setup is owned by the server. The values registered through ``services.AddSyncServer(...)`` win and are pushed to clients automatically.

SyncSetup
^^^^^^^^^^^^^^

``SyncSetup`` exposes the following public properties:

.. code-block:: csharp

    public class SyncSetup : IEquatable<SyncSetup>
    {
        // Tables involved in the sync.
        public SetupTables Tables { get; set; }

        // Filters applied on those tables.
        public SetupFilters Filters { get; set; }

        // Naming prefix/suffix for the metadata generated by DMS.
        public string StoredProceduresPrefix { get; set; }
        public string StoredProceduresSuffix { get; set; }
        public string TriggersPrefix { get; set; }
        public string TriggersSuffix { get; set; }
        public string TrackingTablesPrefix { get; set; }
        public string TrackingTablesSuffix { get; set; }

        // Columns to omit from sync for every table in this setup.
        public SetupColumns ExcludedColumns { get; set; }

        // Process-wide column exclusion list, shared by every SyncSetup instance.
        public static SetupColumns GlobalExcludedColumns { get; }
    }

The constructors accept either an ``IEnumerable<string>`` of table names or ``params string[]``:

.. code-block:: csharp

    var setup = new SyncSetup("ProductCategory", "ProductModel", "Product",
        "Address", "Customer", "CustomerAddress", "SalesOrderHeader", "SalesOrderDetail");


When you call ``SynchronizeAsync(string[] tables)``, ``SyncAgent`` builds a ``SyncSetup`` for you behind the scenes, so these two snippets are equivalent:

.. code-block:: csharp

    var tables = new[] { "ProductCategory", "ProductModel", "Product",
        "Address", "Customer", "CustomerAddress", "SalesOrderHeader", "SalesOrderDetail" };

    var agent = new SyncAgent(clientProvider, serverProvider);
    var r = await agent.SynchronizeAsync(tables);

.. code-block:: csharp

    var setup = new SyncSetup("ProductCategory", "ProductModel", "Product",
        "Address", "Customer", "CustomerAddress", "SalesOrderHeader", "SalesOrderDetail");

    var agent = new SyncAgent(clientProvider, serverProvider);
    var r = await agent.SynchronizeAsync(setup);


Schema
--------------

.. note:: The schema-aware naming is supported by SQL Server (``dbo``, ``SalesLT``...) and PostgreSQL (default ``public``). MySQL/MariaDB and SQLite have no concept of schemas.

You can specify a schema on each table either inline as ``"schema.table"`` or via the ``SchemaName`` property:

.. code-block:: csharp

    // Inline notation
    var tables = new[] { "SalesLT.ProductCategory", "SalesLT.ProductModel", "SalesLT.Product",
        "Address", "Customer", "CustomerAddress" };

.. code-block:: csharp

    // Per-table assignment
    var setup = new SyncSetup("ProductCategory", "ProductModel", "Product",
        "Address", "Customer", "CustomerAddress");

    setup.Tables["ProductCategory"].SchemaName = "SalesLT";
    setup.Tables["ProductModel"].SchemaName = "SalesLT";
    setup.Tables["Product"].SchemaName = "SalesLT";

.. warning:: Schemas are not replicated when the client provider is ``SqliteSyncProvider``, ``MySqlSyncProvider``, or ``MariaDBSyncProvider``. The objects are created in the engine's default namespace.

Filtering columns
-----------------------

Once a ``SyncSetup`` is built, you can pick the columns that should be synced for a specific table:

.. code-block:: csharp

    var setup = new SyncSetup("ProductCategory", "ProductModel", "Product",
        "Address", "Customer", "CustomerAddress", "SalesOrderHeader", "SalesOrderDetail");

    setup.Tables["Customer"].Columns.AddRange(new[] {
        "CustomerID", "EmployeeID", "NameStyle", "FirstName", "LastName" });

    setup.Tables["Address"].Columns.AddRange(new[] {
        "AddressID", "AddressLine1", "City", "PostalCode" });


Only the listed columns will be synced for ``Customer`` and ``Address``.

Excluding columns
^^^^^^^^^^^^^^^^^^^^^

Three exclusion levels are available:

* Per-table: ``setup.Tables["X"].ExcludedColumns`` (or ``ExcludeColumn`` / ``ExcludeColumns``).
* Per-setup: ``setup.ExcludedColumns`` (applies to every table in this setup).
* Process-wide: ``SyncSetup.GlobalExcludedColumns`` (applies to every setup in the AppDomain).

A column listed for exclusion is silently ignored on tables that don't have it. **Primary key columns cannot be excluded.**

.. code-block:: csharp

    var setup = new SyncSetup("Customer", "Address");

    // Per-table, fluent.
    setup.Tables["Address"].ExcludeColumns("SpatialLocation", "Timestamp");

    // Per-table, collection.
    setup.Tables["Customer"].ExcludedColumns.AddRange(new[] { "PasswordHash", "Photo" });

    // Per-setup: applies to every table in this setup.
    setup.ExcludedColumns.Add("CreatedBy");

    // Process-wide: applies to every SyncSetup in the AppDomain.
    SyncSetup.GlobalExcludedColumns.Add("UpdatedOn");

A specific table can opt back in with ``IncludedColumns``:

.. code-block:: csharp

    setup.Tables["AuditLog"].IncludedColumns.Add("UpdatedOn");

The effective column set is: columns that pass the include list in ``Columns`` (if you set any), minus the union of per-table, per-setup, and global exclusions, plus per-table re-includes.

.. note:: Row filters (``SetupFilter`` parameters and ``AddWhere`` clauses) must not reference an excluded column on that table. Foreign key columns that you exclude may cause related ``SyncRelation`` entries to be omitted from the schema, since relation endpoints require synced columns.


Filtering rows
-----------------------

You can also restrict which **rows** are synced from a table. The simplest form is:

.. code-block:: csharp

    setup.Filters.Add("Customer", "CustomerID");
    setup.Filters.Add("CustomerAddress", "CustomerID");
    setup.Filters.Add("SalesOrderHeader", "CustomerID", schemaName: "SalesLT");


Customers, customer addresses, and sales order headers are filtered by ``CustomerID``.

.. note:: Row filtering is rich enough to deserve its own chapter. See `Filters <Filters.html>`_.

Shadow columns and shadow tables
----------------------------------

``SetupTable`` also supports two ways to extend the client schema beyond the server's:

* **Shadow columns** (``AddShadowColumn<T>``): extra columns the client materializes that don't exist on the server. Values are populated server-side, typically inside an ``OnRowsChangesSelected`` interceptor.
* **Shadow tables** (``AsShadowTable``, ``DefineShadowTableColumns``, ``SetupTables.AddShadowTable``): tables provisioned only on the client. The schema lives in the setup; the server emits download rows from an ``OnShadowTableChangesSelecting`` interceptor.

See `Shadow tables and shadow columns <ShadowTables.html>`_ for the full story.


Naming the sync metadata
--------------------------

You can control how DMS names the **tracking tables**, **triggers**, and **stored procedures** it generates:

.. code-block:: csharp

    var setup = new SyncSetup(tables)
    {
        StoredProceduresPrefix = "s",
        StoredProceduresSuffix = "",
        TrackingTablesPrefix = "t",
        TrackingTablesSuffix = "",
        TriggersPrefix = "",
        TriggersSuffix = "t",
    };

HTTP mode
---------------

In HTTP mode, the setup lives on the server. Configure it from ``Program.cs`` (or ``Startup.cs``) when registering the sync server:

.. code-block:: csharp

    var builder = WebApplication.CreateBuilder(args);

    builder.Services.AddControllers();
    builder.Services.AddDistributedMemoryCache();
    builder.Services.AddSession(options => options.IdleTimeout = TimeSpan.FromMinutes(30));

    var connectionString = builder.Configuration.GetConnectionString("DefaultConnection");

    var setup = new SyncSetup("ProductCategory", "ProductDescription", "ProductModel",
        "Product", "ProductModelProductDescription",
        "Address", "Customer", "CustomerAddress",
        "SalesOrderHeader", "SalesOrderDetail")
    {
        StoredProceduresPrefix = "s",
        TrackingTablesPrefix = "t",
        TriggersSuffix = "t",
    };

    // Register a server provider instance.
    builder.Services.AddSyncServer(new SqlSyncProvider(connectionString), setup);

    var app = builder.Build();
    app.UseRouting();
    app.UseSession();
    app.MapControllers();
    app.Run();


.. warning:: The prefix and suffix properties are part of the setup but they are **not** shared between server and client metadata tables. Each side names its own objects however it wants. What matters for compatibility is that the SyncSetup signatures (table names and column lists) match between sides.


SyncOptions
^^^^^^^^^^^^^^

``SyncOptions`` is the per-process configuration. It can have different values on each side.

.. code-block:: csharp

    public class SyncOptions
    {
        public const string DefaultScopeInfoTableName = "scope_info";
        public const string DefaultScopeName = "DefaultScope";

        // Tmp directory used for batch files.
        // Default: [User Temp Path]/DotmimSync.
        public string BatchDirectory { get; set; }

        // Where snapshots are stored. Server side only when using HTTP.
        public string SnapshotsDirectory { get; set; }

        // Approximate batch file size in KB. Min 100. Default 2000.
        public int BatchSize { get; set; }

        // When true, error messages include sensitive details. Default true.
        public bool UseVerboseErrors { get; set; }

        // Auto-clean tracking metadata after a successful sync. Default true.
        public bool CleanMetadatas { get; set; }

        // Auto-delete tmp batch directory after a successful sync. Default true.
        public bool CleanFolder { get; set; }

        // Disable database constraints during apply. Default false.
        public bool DisableConstraintsOnApplyChanges { get; set; }

        // Custom name for the scope_info table. Default "scope_info".
        public string ScopeInfoTableName { get; set; }

        // Default conflict policy. May be overridden by the server. Default ServerWins.
        public ConflictResolutionPolicy ConflictResolutionPolicy { get; set; }

        // Default error resolution policy. Can differ between server and client. Default Throw.
        public ErrorResolution ErrorResolutionPolicy { get; set; }

        // ILogger to receive sync messages.
        public ILogger Logger { get; set; }

        // Verbosity of progress events. Default Information.
        public SyncProgressLevel ProgressLevel { get; set; }

        // Optional command timeout, in seconds. Default null (provider default).
        public int? DbCommandTimeout { get; set; }

        // Transaction mode used when applying changes. Default AllOrNothing.
        public TransactionMode TransactionMode { get; set; }

        // Resumable transport. Default false. See "Resumable sync" in Synchronize.
        public bool Resumable { get; set; }

        // Optional factory used to build the SessionId for a sync session.
        // Used by resumable orchestrators to reattach to a previous session.
        public Func<string, Guid> SessionIdProvider { get; set; }
    }

.. note:: If you do not pass a ``SyncOptions`` to ``SyncAgent``, a default instance is created.

A few useful static helpers:

.. code-block:: csharp

    // Default batch directory full path: [User Temp Path]/DotmimSync.
    public static string GetDefaultUserBatchDirectory();

    // Default user temp folder.
    public static string GetDefaultUserTempPath();

    // Default sync tmp folder name (always "DotmimSync").
    public static string GetDefaultUserBatchDirectoryName();


Batch mode
----------------

Batching is essential for large syncs. By default DMS streams batch files to disk, with each file targeting approximately ``BatchSize`` KB. The default ``BatchSize`` is ``2000`` (about 2 MB per file). The minimum is ``100``; smaller values are clamped automatically.

.. code-block:: csharp

    var clientOptions = new SyncOptions { BatchSize = 500 };


.. warning:: ``BatchSize`` is approximate. The on-disk size depends on the serializer (JSON by default), compression, and converters. Tune it for your workload.


.. hint:: Sample: `Batch size sample <https://github.com/Mimetis/Dotmim.Sync/tree/master/Samples/BatchSize>`_

For example, after inserting **100000** product category items on the server:

.. code-block:: sql

    INSERT INTO ProductCategory (Name)
    SELECT SUBSTRING(CONVERT(varchar(255), NEWID()), 0, 7)
    GO 100000

The server splits the response into multiple batch files; the client downloads them one at a time and applies them as they arrive. With small ``BatchSize`` values the client uses less memory but makes more requests; with large values it makes fewer, bigger requests. Tune to your network and memory budget.

.. hint:: In HTTP mode the **client** dictates batching. The server adapts its payloads accordingly.


Bulk operations on SQL Server
--------------------------------

When the provider is ``SqlSyncProvider`` (or ``SqlSyncChangeTrackingProvider``) DMS uses **Table Valued Parameters** (TVPs) to apply changes in bulk. This is controlled by the ``UseBulkOperations`` property on the provider itself (default ``true``):

.. code-block:: csharp

    var serverProvider = new SqlSyncProvider(serverConnectionString)
    {
        UseBulkOperations = true,
    };

When enabled, additional stored procedures and one TVP type are generated per table: ``<Table>_bulkdelete``, ``<Table>_bulkupdate``, and ``<Table>_BulkType``.

.. note:: ``UseBulkOperations`` is provider-level, not part of ``SyncOptions``. Other providers either ignore this property or implement their own bulk pathway internally.

Bulk paths exist for SQL Server (TVPs), PostgreSQL (``COPY FROM STDIN``), and SQLite (staging table + ``INSERT OR REPLACE``). See `Bulk operations <Bulk.html>`_ for the full story including ``BulkBatchMaxLinesCount`` tuning and how to verify bulk is engaged.


CleanMetadatas
----------------------

When ``CleanMetadatas`` is ``true`` (default), the client deletes T-2 (and older) metadata rows from its tracking tables after every successful sync.

* The cleanup runs only when the client actually downloaded something.
* T-1 metadata is preserved for safety.

You can also clean metadata explicitly on either side:

.. code-block:: csharp

    var localOrchestrator = new LocalOrchestrator(clientProvider);
    var cleaned = await localOrchestrator.DeleteMetadatasAsync();

.. note:: When using ``SqlSyncChangeTrackingProvider``, metadata cleanup is delegated to SQL Server's Change Tracking subsystem.

See `Metadatas <Metadatas.html>`_ for the server-side counterpart.


DisableConstraintsOnApplyChanges
-----------------------------------

When ``true``, DMS disables database constraints (or pulls similar tricks at the connection or table level depending on the provider) before applying changes, then reenables them after. Useful when you can't be sure of the table apply order or when you intentionally apply rows out of FK order. Default is ``false``.


ScopeInfoTableName
-------------------------

Customize the scope info table name. Default ``scope_info``. The companion table for client scope is named by appending ``_client`` to this value.


ConflictResolutionPolicy
------------------------------

Default conflict resolution policy. The server's value wins in HTTP scenarios. See `Conflict <Conflict.html>`_.


ErrorResolutionPolicy
------------------------------

Default error resolution policy when an apply fails locally. Can differ on each side. See `Errors <Errors.html>`_.


TransactionMode
------------------------------

How DMS wraps the apply phase in transactions:

* ``AllOrNothing`` (default): the entire batch info is applied inside a single transaction. If anything fails, everything rolls back.
* ``PerBatch``: each batch part file is applied in its own transaction.
* ``None``: no transaction during apply (very risky, no rollback).


Resumable & SessionIdProvider
------------------------------

Set ``Resumable = true`` to keep enough state on disk to resume an interrupted HTTP sync from the last successfully transferred batch on the next call. ``SessionIdProvider`` is the seam used by the resumable transport to reattach to a previous session id; you can also override it for sticky session id scenarios.

See `Resumable sync <Resume.html>`_ for the full story (state stores, server-side ``SessionStore``, end-to-end examples) and "Resumable sync" in `Synchronization types <Synchronize.html>`_ for the per-call override.
